# Native DLSS для Lossless Scaling 0.3.2

Выбор генератора и его настройки встроены в родное окно LS.
В **Frame Generation → Type** появился пункт **DLSS**.
При выборе DLSS используется экономичный backend ×2 SDR: NVIDIA Optical Flow
и DLSS, с обходом проверенных GPU-проходов генератора LS.
При выборе существующих LSFG-типов используются штатные обработчики и генерация LS.

В 0.3.2 исправлено игнорирование `GPUOrdered` из INI при управлении через
родной интерфейс. По умолчанию остаётся `GPUOrdered=1`; режим 0 теперь
действительно доступен для сравнения после полного перезапуска LS.
Поток логирования больше не делает GPU-readback под блокировкой backend.
Прогрев учитывается отдельно от отсутствия пары кадров. Исправление запуска
интерфейса из 0.3.1 сохранено.

Эта версия расширяет диагностику рывков. Устранение просадок 118→104 FPS
на физических RTX 3080 ещё не подтверждено.

## Установка

1. Полностью закрой LS, включая значок в трее.
2. Распакуй весь пакет в отдельную папку. Запусти `Install.cmd` и выбери папку LS.
3. Запусти LS. В нужном профиле выбери **Frame Generation → Type → DLSS**.
4. Настрой Optical Flow в появившейся карточке. Для возврата к генератору LS
   выбери прежний тип в этом же списке.

Копировать `Settings.cmd` в папку LS не требуется. Это старый редактор INI;
после установки 0.3.0 источником выбора генератора служит профиль в интерфейсе LS.
Пакет не содержит чужую изменённую DLL интерфейса: установщик патчит твою
локальную `LosslessScaling.dll` с проверкой точного SHA256.
Поддерживается именно версия LS 3.2.2 из ранее предоставленного архива.

Установщик снимает метку скачивания Windows только с трёх DLL своего пакета
до загрузки `Mono.Cecil.dll` и копирования файлов. Это устраняет ошибку
`LoadFrom / 0x80131515` после распаковки скачанного ZIP. Если снять метку
не удалось, открой свойства самого ZIP, нажми «Разблокировать» → «Применить»,
затем распакуй его заново и повтори установку.

Установщик сохраняет предыдущие DLL и настройки в `native-dlss-backups`.
Профили LS и старые значения `NativeDLSS.ini` сохраняются.
При первом открытии параметры DLSS наследуются из старого INI, включая
явно выбранный в нём профиль. После сохранения в LS они принадлежат
конкретному родному профилю LS; копирование профиля копирует и параметры DLSS.

Для отката закрой LS и запусти `Restore.cmd`. При возврате к старому интерфейсу
сохранённое значение DLSS заменяется на LSFG3, чтобы старый LS смог открыть
профиль. Остальные текущие настройки профилей сохраняются. SM86-файлы,
настройки NVIDIA Inspector и G-SYNC установщик не меняет.

## Настройки внутри LS

- Optical Flow: FAST / MEDIUM / SLOW, сетка 4×4 / 2×2.
- Разрешение анализа: 10–100% от захваченного изображения.
- Число кадров в обработке: 2–4.
- Фильтр одинаковых кадров и сброс истории при смене сцены.
- Допуски фильтров и до восьми прямоугольников HUD в процентах.
  После ввода нажми «Сохранить параметры фильтров и HUD».

**Изменения качества Optical Flow, разрешения анализа и числа кадров требуют
полного перезапуска LS.** Уже созданный GPU-граф сохраняется между повторными
запусками FG; безопасная пересборка качества на лету пока не реализована.
Пункт Type, фильтры и HUD передаются через обычное применение профиля LS.
Горячие клавиши Ctrl+Alt+F6/F8 не меняют выбор из родного интерфейса.
Ctrl+Alt+F7 по-прежнему сбрасывает историю backend.

DLSS в этом билде — только ×2 SDR. Множитель и HDR штатного генератора,
сохранённые в профиле, остаются доступны при возврате к его типу.
В областях HUD используется текущий исходный кадр.
Повторы проверяются по RGB на GPU; этот фильтр не отменяет вызов NGX/NVOF.
Смена сцены определяется по доле изменившихся пикселей; пороги настраиваются.

## Проверка

Покадровая диагностика включена по умолчанию. В `NativeDLSS.ini`, секция
`[Diagnostics]`: `Level=2` — события и распределения, `Level=1` — только
распределения/счётчики, `Level=0` — счётчики. `IntervalMs=1000` задаёт
интервал записи; `FrameEvery=1` сохраняет каждый кадр (при увеличении
распределения продолжают учитывать все полученные события). После изменения
диагностики полностью перезапусти LS. Для проверки влияния диагностики
сравни Level 2 и 0 в одинаковой сцене.

`MaxLogMiB=16`, `KeepLogFiles=4` ограничивают хранение текущим файлом и
тремя предыдущими частями. Размер может превысить порог на один пакет записи.
Не увеличивай размер части выше 25 MiB при использовании штатного сборщика:
он пропускает отдельные файлы больше 25 MiB и общий объём больше 100 MiB.

Лог содержит исходные и переданные LS параметры, запрошенную и реально
созданную конфигурацию GPU, `restart_pending`, адаптеры/LUID, номинальную
частоту экрана, память, CPU/IO процесса, хеши загруженных модулей, тайминги
SDK, короткие p50/p95/p99/max, состояние очередей и причины повторов.
Флаги завершённых GPU-заданий связываются с подмешиванием через
`context/epoch/generation/ready`. `4294967295` означает неизвестный флаг,
а `-1` — недоступное время. Числа относятся к наблюдениям LS, не к ID кадров игры.
`completed.qpc` — момент чтения уже завершённых метаданных на CPU.

`wait_api_cpu_ms` измеряет только CPU-вызов GPU Wait, а не ожидание на GPU.
`backend_span_gpu_ms` включает подготовку, зависимость NVOF, генерацию и
постобработку; начальные D3D11-копии, ожидание producer до первого timestamp,
подмешивание и показ не входят. `interpolation_allowed_samples` — разрешение
shader, а не число реально показанных сгенерированных кадров. Часть последних
метаданных остаётся `unpolled_jobs` до следующего исходного кадра; при потере
записи или переподключении это явно учитывается.

Для сопоставления игры и вывода LS запусти **Capture-Pacing.cmd** из пакета
при уже работающих игре и FG. Укажи имя exe игры; сбор длится 120 секунд.
В пакете есть оригинальный PresentMon 2.6.0 с проверкой SHA256. Скрипт
читает ETW, пишет CSV в `LS/logs`, не внедряется в процесс игры и не меняет
настройки вывода. Если ETW отказывает в доступе, запусти этот cmd от
администратора. Затем **Collect-Logs.cmd** собирает также CSV и его метаданные.
При недоступных ETW-событиях часть display/GPU-полей может остаться пустой.
ETW не является физическим измерением VRR или полной задержки мышь→экран.

REA действительно использован для анализа managed DLL, обработчиков Type,
сохранения профиля и native ApplySettings. Метаданные и ограниченные результаты
описаны в `analysis/REA-NATIVE-UI.md` репозитория.
Повторная проверка native REA, диагностика 0.3.2 и оценка Reflex/Frame Warp:
`analysis/DIAGNOSTICS-0.3.2-REFLEX.md` в репозитории.

Пункт DLSS сохраняет захват, ресурсы LS, его расписание кадров и Present.
Проверенные dispatch генератора обходятся после подтверждения финального
прохода на текущем контексте. Прогрев, неизвестный участок или ошибка
инициализации остаются защитными случаями; работа каждого GPU-прохода не
удалена физически из программы. Логи позволяют проверить фактический режим:
`ui_owned=1 ui_type=6 requested_mode=dlss_economy`, рост `analysis_skipped`,
`synthesis_skipped` и заданий DLSS. При штатном типе ожидается
`requested_mode=ls_native` и `ui_type`, соответствующий выбранному типу.

`Collect-Logs.cmd` собирает диагностические логи, в том числе `native-ui.log`,
и информацию о runtime. Он не включает DLL.
После установки проверь чистый запуск, переключение DLSS → LSFG → DLSS,
сворачивание, возврат к целевому окну и повторные остановки/запуски FG.
Новая аппаратная проверка на твоих RTX 3080, SM86 и VRR ещё нужна:
тесты WARP и WPF не подтверждают работу DLSS на физической видеокарте.

Если LS не открывается, запусти `Start-Diagnostics.cmd` из пакета и выбери
папку LS. Он запускает LS с записью stderr и трассы загрузчика .NET;
консоль остаётся открытой до закрытия LS. Затем запусти `Collect-Logs.cmd`
и передай полученный ZIP. DLL и содержимое профилей в него не включаются.
